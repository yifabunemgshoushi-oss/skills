# 任务模板与编排示例

从 [SKILL.md](../SKILL.md) 进入，只读本次任务对应的小节。以下模板用于已确定需要委派的任务；尖括号内容由主代理按实际情况填写，具体工具名和路径以当前环境为准。

## 检索：交回可直接使用的定位结果

适用于 Explore。示例把属于同一行为链的问题合在一起；需要完整理解或复核实现时，按主文选择具备相应能力的代理。

```text
任务与用途：
定位接入闲置引导所需的现有链路。交回提示表现入口、玩家活动重置入口、暂停守卫和修改落点，供主代理编辑已定位文件。

已知：<已确认的需求、符号或文件线索；未知内容明确标注>。
边界：你负责运行时链路；autoTips 的类型、解析值与数组边界由配置调查者负责。遇到配置问题返回指针，不另做完整调查。只读，不修改文件。

约束：使用简体中文。<本任务必需的规范、工具路由、现有改动及环境限制>。
交付：先给接入结论，再列各入口的 file:line、最小必要片段和未确认项。
停止：上述入口与修改落点都有证据即可返回；某项不存在时，说明已查范围与依据。关键工具或输入缺失时，报告已完成部分和最小缺口。
```

回报示例：

```text
状态：完成 / 部分完成 / 阻塞
结论：<可复用入口与接入位置，或不存在的证据>
证据：<file:line + 必要片段>
未确认：<影响下一步的具体缺口；没有则写无>
```

## 复现：先拿到稳定失败，再判断是否值得缩小

适用于 general-purpose。首个产物优先覆盖用户症状所在的真实输入与调用分支；稳定失败已能保护修复时即可交接。只有简化能明显降低维护成本或提高判别力时，再追加有明确终点的最小化任务，避免为了理想构造持续生成脚本。

```text
任务与用途：
为 <用户症状> 建立可执行复现，主代理将据此修复并加入回归覆盖。

已知：<真实输入、入口、当前行为与期望行为；期望依据来自哪里>。
边界：只负责复现，不修改生产代码。可写 <临时目录>；复用已有脚本和数据。主代理负责修复，<负责人> 负责规范定位。

约束：使用简体中文。<必要规范、工具路由、环境限制>。
交付：脚本和输入路径、运行命令与退出码、实际和期望行为、失败断言或关键输出，以及已确认覆盖的真实分支。
停止：同一输入能重复触发目标差异，且证据足以定位修复和设计回归即可返回。无法复现时，交回已试输入、观察结果及最小缺口。
```

回报示例：

```text
状态：完成 / 未复现 / 阻塞
产物：<脚本、数据路径>
复现：<命令、退出码、关键失败输出>
实际与期望：<具体行为及期望依据>
覆盖与限制：<真实入口、分支；模拟或缺失的部分>
```

## 验证：完整留证，摘要归因

适用于 general-purpose。验证规则以主文第 5 步为准；模板中的检查范围必须来自仓库约定和本次改动。

```text
任务与用途：
验证 <变更目标> 是否满足 <验收条件>，交回可据以收尾的检查结果。

输入：<变更文件、相关未提交改动、复现产物、已跑检查、仓库验证约定与命令入口>。
边界：运行必要检查并分析结果，不修改生产代码、测试或基线。临时文件和完整日志可写 <目录>；发现问题交回主代理修复。

约束：使用简体中文，遵循仓库规定的检查顺序。<当前版本、环境限制、已知失败的对照证据>。
交付：记录验证起止时间和工作区基准；按下列格式汇总全部失败，并列出未执行项及原因。
停止：约定检查完成且结果可追溯即可返回。环境阻塞时保留现有日志，说明哪些检查仍可独立执行；需要更改验证输入时先交回主代理。
```

回报示例：

```text
状态：通过 / 有失败 / 部分验证 / 阻塞
范围：<commit、未提交改动摘要、验证起止时间>
检查：<命令、退出码、pass/fail/skip 数量（适用时）、耗时、完整日志路径>
失败：<全部失败项或同类错误分组、关键输出、明细路径>
归因：<本次引入 / 有证据的既有失败 / 未确认；对应对照证据>
未执行：<检查与原因；没有则写无>
限制：<尚未覆盖的运行环境或用户行为>
```

## 依赖示例：闲置引导

示例假设 AGENTS.md 已确定运行时链路、配置调查和完整验证需要委派。命名只是帮助说明组织方式，不要求固定派三个代理。

| 工作 | 主责与产物 | 启动所需输入 |
|---|---|---|
| 运行时链路 | Explore：表现入口、活动入口、暂停守卫、修改落点 | 已确认的用户目标 |
| 配置边界 | Explore：类型、实际解析值、样本与数组边界 | 配置调查范围 |
| 整合编辑 | 主代理：实现与必要的局部验证 | 对应修改所需的链路或配置结论 |
| 完整验证 | general-purpose：约定检查、全部失败、日志 | 实现稳定及验收范围 |

实际调度：

1. 两项调查互不依赖，在同一轮调用中按宿主接口启用后台；提供 `run_in_background` 时分别设为 `true`。主代理检查工作区已有改动，必要且不依赖调查结论的用户澄清同步进行；受答案影响的方案深化等待关键意图明确。
2. 运行时链路先回报，就先验收。若它足以支持相关编辑，主代理开始这部分；依赖配置边界的编辑仍等待配置结果。配置解析问题始终由配置调查者负责。
3. 配置结果回报后，核实其建议成立的条件，再整合实现。若发现已闭合问题无需继续调查，就及时收尾该任务。
4. 用户追加“暂停时不触发、点空白或拖动也重置”时，先判断现有证据是否已覆盖；有缺口才向原调查者补充需求和验收条件。其他独立工作继续。
5. 代码和相关测试稳定后交接完整验证。验证期间主代理可整理交付说明；相关输入若变化，则更新验证范围并重跑受影响检查。
6. 某项失败发生在未改动文件中，仍完整报告；找到基线或变更前证据才能归为既有失败，否则保留未确认状态。主代理据结果完成修复或明确披露阻塞与限制。

## 交付前的场景自检

修改这份技能或评估实际编排时，检查它是否能导出下列动作；文档自检不能替代真实会话验证。

| 场景 | 应出现的动作 |
|---|---|
| 两项独立任务，其中一个很慢 | 可用结果先被验收和消费；无关慢任务不阻塞已就绪动作 |
| 多个任务都暂未完成，主代理没有独立工作 | 使用阻塞等待，或交还宿主等待通知与自动唤醒；缺少这两种能力时按主文处理回收限制 |
| 回报很短，却漏了关键反例 | 按证据缺口补问，不以字数合格代替验收 |
| 两个代理得出冲突结论 | 对齐输入、版本和口径，再针对分歧补证据 |
| 稳定复现已经交付 | 先用于修复；仅在收益明确时继续缩小构造 |
| 检查失败但报错文件没改过 | 保留失败项，用对照证据判断归因 |
| 验证期间相关输入发生变化 | 已有结果只证明原输入，重跑受影响检查 |
| 用户新增要求或取消某项要求 | 更新受影响任务，收尾已无用途的任务 |
